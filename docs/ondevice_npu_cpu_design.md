# 온디바이스 ThinKV: VENTUNO Q에서 NPU + CPU 분업 설계 (2026-11-16 초안, 2026-11-19 갱신)

근거: 2026-11-16 사용자와의 설계 대화, `docs/e10_ct_kernel_design.md`(E10, 블록 테이블), `docs/e4_tbe_tbq_design.md`(TBE·TBQ), Obsidian `version2/우려사항/온디바이스 실행 범위.md`·`version2/디바이스/디바이스 비교.md`.
이 문서의 시간·계산량 숫자는 **모두 계산으로 낸 추정값**이다. 실측이 나오면 9절에 기록하고 추정값을 고친다.

## 0. 목표와 범위

- **목표**: VENTUNO Q(Qualcomm IQ-8275, RAM 16GB)에 ThinKV(TBQ 양자화 + TBE 퇴출)를 적용한 모델을 올린다. KV 캐시 메모리를 **실제로** 줄이고, NPU와 CPU를 함께 써서 속도도 낸다.
- **모델**: **DeepSeek-R1-Distill-Llama-8B**(32층, 은닉 4096, 쿼리 헤드 32, KV 헤드 8, 헤드 차원 128). vast.ai GPU에서 돌린 것과 같은 모델을 쓴다(2026-11-16 사용자 결정. 초안은 Obsidian 노트를 따라 Qwen3-1.7B로 잘못 가정했다). 숫자는 이 모델 기준이다. 코드는 층 수·헤드 수를 모델 설정에서 읽고 박아 넣지 않는다.
- **우리 범위(2026-11-16 사용자 결정)**: **모델과 코드 구현까지.** 보드에 올려 돌리고 재는 일(NPU 컴파일, M0·M4~M6의 보드 실행)은 **다른 팀원**이 한다. 우리가 넘기는 것은 ① Mac에서 검증된 `ondevice/` 코드 ② NPU에 올릴 수 있게 층 단위 조각으로 나눈 모델 ③ 팀원이 따라 할 실행·측정 안내(`ondevice/README.md`)다.
- **범위 밖**: 벤더 실행기(GenieX) 안에 ThinKV 넣기(KV가 int8·고정 길이로 컴파일돼 불가능), Adreno GPU 경로, Triton 커널의 보드 이식(Triton은 NVIDIA·AMD GPU 전용).

## 1. 결정 사항

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 칩 분업 | **NPU**: 가중치 계산(정규화, Q·K·V 투영, 출력 투영, MLP). **CPU**: KV 양자화 저장, 퇴출, 빈칸 재사용, 어텐션 | 2026-11-16 사용자 결정("NPU랑 CPU 같이 활용"). 어텐션은 KV 길이·비트 수·살아 있는 칸이 매 토큰 바뀌어 고정 모양만 받는 NPU에 넣을 수 없다 |

## 2. 전체 구조

```
보드 RAM 16GB (CPU·NPU 공용)
 ├ 모델 가중치 (NPU용)
 ├ 프롬프트 KV: bf16, 연속 배열, 퇴출 없음
 ├ 생성 토큰 KV: 4비트 풀(R·E) + 2비트 풀(T), 스케일 표, 빈칸 재사용
 ├ 열린 묶음 버퍼: 아직 16개가 안 찬 최근 토큰, bf16
 └ 장부: BlockTable 두 개(풀마다 하나), 슬롯 → 묶음 번호 표
```

**토큰 하나 생성(decode)**, 층 l = 0..31:

```
NPU 조각 l   : [층 l-1의 출력 투영 + MLP] + [층 l의 정규화 + Q·K·V 투영]   → q, k, v
CPU          : RoPE → k·v를 열린 묶음 버퍼에 추가 → (16개가 차면 양자화해 풀에 저장)
CPU          : 퇴출 계획 적용(빈칸 표시) → 융합 어텐션(프롬프트 bf16 + 풀 + 버퍼)
마지막 조각  : [층 31의 출력 투영 + MLP] + 최종 정규화 + 출력층
```

**앞 층의 뒤 조각과 다음 층의 앞 조각을 하나로 묶는다.** NPU 호출이 토큰당 64번이 아니라 **33번**이 된다. 조각 0은 임베딩 뒤부터 시작한다.

## 3. NPU 쪽

- **조각 모양**: 입력은 은닉 상태 `[n, 4096]`와 어텐션 출력, 출력은 q·k·v와 잔차용 은닉 상태다. decode용(n = 1)과 prefill용(n = 128) 두 벌을 컴파일한다. prefill의 마지막 묶음은 채워서 크기를 맞추고, 채운 자리는 버린다.
- RoPE는 위치에 따라 달라지므로 CPU에서 한다. (Llama 계열에는 q·k 정규화 층이 없다. 그런 층이 있는 모델이면 NPU 조각에 넣는다.)
- **가중치·활성값 정밀도**: NPU가 요구하는 대로 따른다(결정 10, 벤더 기본 w4a16에서 시작). 보드에서의 정확도는 GPU bf16 결과와 다를 수 있고, 보드에서 따로 잰 값으로 보고한다.
- **컴파일 도구는 미정이다**(7절 R2). 후보는 QAIRT 직접 사용, ExecuTorch Qualcomm 백엔드.
- 두 벌의 조각이 가중치를 메모리에서 공유하는지 도구에서 확인한다. 공유가 안 되면 가중치가 두 번 올라간다.

## 4. KV 저장 형식

**구간 세 개.** 지금 `press.py`의 동작을 그대로 따른다.

| 구간 | 정밀도 | 퇴출 | 저장 |
|---|---|---|---|
| 프롬프트 | 모델 정밀도(보드 bf16) | 없음 | 연속 배열 `[prompt_len, Hkv, D]` |
| 열린 묶음(최근 16개 미만) | 모델 정밀도(보드 bf16) | 없음 | 고정 버퍼 `[16, Hkv, D]` |
| 양자화된 생성 토큰 | R·E는 4비트, T는 2비트 | TBE | 풀 두 개 + 스케일 표 |

**양자화 단위**(`thinkv/quant.py`와 같다). 묶음 하나 = 같은 구간의 연속 16토큰 = 양자화 호출 한 번.
- **키**: 채널마다 토큰 16개가 스케일 하나를 같이 쓴다. 스케일은 묶음당 `[Hkv, D]`.
- **값**: 토큰마다 채널 16개가 스케일 하나를 같이 쓴다. 스케일은 토큰당 `[Hkv, D/16]`.
- 스케일은 E4M3 1바이트로 저장하고, 호출마다 전역 배율 `glob`(float32) 하나를 둔다.

**코드**
- NVFP4(4비트): 부호 1비트 + 격자 `{0, .5, 1, 1.5, 2, 3, 4, 6}`의 번호 3비트. 한 바이트에 2개.
- ternary(2비트): `{-1, 0, +1}`. 한 바이트에 4개.
- 비트 배치는 앞 채널이 아래 비트다(결정 21).

**배열**(층마다, 풀마다)

| 배열 | 모양 | 타입 |
|---|---|---|
| `k_code`, `v_code` | `[num_slots, Hkv, D × 비트 / 8]` | uint8 |
| `v_scale` | `[num_slots, Hkv, D/16]` | uint8 (E4M3) |
| `slot_gid` | `[num_slots]` | int32. 이 슬롯이 속한 묶음 번호 |
| `k_scale` | `[num_groups, Hkv, D]` | uint8 (E4M3) |
| `k_glob`, `v_glob` | `[num_groups]` | float32 |
| `live_mask` | `[num_slots]` | uint8. `BlockTable.live_mask`와 같다 |

**키 스케일은 슬롯이 아니라 묶음 번호로 찾는다.** 그래서 빈칸 재사용을 토큰 단위로 해도 된다(E10 백로그 D8의 함정을 이렇게 피한다). 묶음의 스케일 행은 그 묶음의 토큰이 모두 퇴출되면 반납한다(묶음별 살아 있는 토큰 수를 센다).

**풀 두 개.** 블록 유형이 할당 때 고정되므로(E10 결정) 4비트 풀은 R·E 블록, 2비트 풀은 T 블록만 담는다. 풀마다 `BlockTable` 하나를 둔다. 4비트 풀 안에서 R과 E는 서로 다른 유형으로 넘겨 빈칸을 섞어 쓰지 않는다(결정 16). `block_table.py`는 고치지 않는다.

**풀 크기(2026-11-19 변경).** 풀은 **0에서 시작해 쓰는 만큼 늘린다.** 미리 잡는 것은 장부(`BlockTable`)뿐이고, 최대 생성 길이만큼 잡는다(블록당 수십 바이트). 초안은 "예산(k + τ 토큰)만큼 미리 잡는다"였으나, 예산은 상한이 아니다. 닫힌 구간이 모두 보존 바닥에 닿으면 퇴출 계획이 더 줄이지 못하고 예산을 넘긴다.

**토큰당 메모리**(층 하나, 바이트)

| 방식 | 키 | 값 | 값 스케일 | 키 스케일 | 묶음 번호 | 합 | bf16 대비 |
|---|---|---|---|---|---|---|---|
| bf16 | 2048 | 2048 | - | - | - | 4096 | 1× |
| 4비트 | 512 | 512 | 64 | 64 | 4 | 1156 | 3.5× |
| 2비트 | 256 | 256 | 64 | 64 | 4 | 644 | 6.4× |
| 4비트, 최악 | 512 | 512 | 64 | 1024 | 4 | 2116 | 1.9× |

"최악"은 퇴출 뒤 묶음마다 토큰이 하나씩만 살아남은 경우다. 키 스케일 한 행(1024바이트)을 토큰 하나가 차지한다(7절 R4).

## 5. CPU 쪽

**쓰기**
1. 새 k·v를 열린 묶음 버퍼에 넣는다.
2. 16개가 차면 유형에 맞는 방식으로 양자화하고, `BlockTable.append()`가 준 슬롯 16개에 코드를 쓴다. 묶음 번호를 새로 받아 `slot_gid`와 스케일 표에 기록한다.

**퇴출**
- 퇴출 계획은 `ThinKVPress.plan_step()`의 논리를 `ondevice/`로 옮겨 쓴다(구간·예산·보존 단계. 결정 15).
- 남길 토큰은 `select_representative_tokens`(K-means)로 고른다. 입력은 그 구간의 키를 풀어 낸 값이다. 퇴출 때만 하는 일이라 임시 메모리는 구간 하나(최대 128토큰)분이다.
- 고른 뒤 `BlockTable.evict()`로 빈칸 표시만 한다.

**decode 융합 어텐션 커널** (C++/NEON, 새로 작성. 처음 불릴 때 자동 컴파일, ctypes 호출, OpenMP로 KV 헤드별 병렬. 결정 17)
- 입력: q `[Hq, D]`, 프롬프트 KV(bf16), 풀 두 개, 열린 묶음 버퍼, `live_mask`, `slot_gid`, 스케일 표. 출력: `[Hq, D]`.
- GQA 규칙은 `kernels/reference.py`와 같다(쿼리 헤드 h는 KV 헤드 `h // (Hq // Hkv)`, 이 모델은 `h // 4`).
- 키 쪽 요령: 묶음마다 `q' = q × k_scale[gid] × k_glob[gid]`를 먼저 만들어 두면, 안쪽 루프는 `q'`와 정수 코드의 내적만 남는다. 묶음 수는 토큰 수의 1/16 수준이라 준비 비용이 작다.
- 값 쪽 요령: 확률 `p_n`에 토큰의 값 스케일을 곱한 뒤 정수 코드를 누적한다.
- softmax는 세 구간(프롬프트, 풀, 버퍼)의 점수를 합쳐서 한 번에 한다.

**희소도 측정(사고 유형 분류)**
- 측정 층(24)에서는 `press.py`의 `phi_win256_mid`와 같은 값을 내야 한다. 이 함수는 캐시의 **논리 순서**로 최근 256칸을 본다(앞 4칸과 마지막 8칸 제외).
- 슬롯은 물리적으로 섞여 있으므로, 장부(`Seq.segments`의 슬롯 목록)에서 "살아 있는 최근 256개 슬롯을 순서대로" 뽑아 그 키만 점수를 낸다. 이 계산은 커널 밖 파이썬에서 한다(결정 18).

**prefill**
- 어텐션은 PyTorch `scaled_dot_product_attention`. 묶음 128토큰의 q와 지금까지의 프롬프트 KV(bf16) 전체.
- 프롬프트 KV 배열은 처음에 프롬프트 길이만큼 한 번만 잡는다.

## 6. 작업 순서와 검증

**담당**: M1~M3과 M3.5는 우리(Mac). M0·M4~M6은 보드 담당 팀원이 실행하고, 우리는 그때 필요한 코드와 안내를 준비한다. Mac에서는 NPU 조각 자리에 같은 조각을 PyTorch로 돌리는 대역을 끼워 전체 흐름을 검증한다.

| 단계 | 내용 | 통과 기준 | 어디서 |
|---|---|---|---|
| **M0** | 보드 사전 측정: ① 조각 하나를 NPU용으로 컴파일해 호출 왕복 시간 ② 컴파일 도구 확정 ③ CPU 메모리 대역폭(memcpy) | 왕복 × 33이 토큰당 목표 시간 안에 든다. 안 되면 7절 R1 대안으로 간다 | 보드 |
| **M1** | 압축 저장: 양자화 → 코드·스케일 → 풀기 | 풀어 낸 값이 `FQ[kind]` 출력과 비트 단위로 같다(V1). 두 방식(nvfp4, ternary) 모두. kivi2는 논문 기준선이라 온디바이스 저장 형식에 넣지 않는다(2026-11-16 사용자 확정) | Mac |

| **M4** | NPU 조각 연결(decode), 전체 CPU 실행과 비교 | 고정 문제 몇 개에서 출력이 정상이고 답이 맞는다(V4). GPU 결과와 토큰이 같을 필요는 없다(결정 7) | 보드 |
| **M5** | prefill 묶음 실행 | 묶음 실행의 프롬프트 KV가 한 번에 넣은 결과와 허용 오차 안에서 같다(V5) | 보드 |
| **M6** | 측정 | 9절 표를 채운다 | 보드 |

**측정 항목(M6)**: 같은 KV 예산에서 무압축 대비 최대 컨텍스트 길이, 최대 상주 메모리, 첫 토큰 지연, 토큰당 지연, 토큰당 NPU 시간과 CPU 어텐션 시간의 비율. 대조군은 벤더 NPU 경로(GenieX)와 전부 CPU 실행.

## 8. 추정값 (실측 전)

**decode에서 KV 때문에 오가는 메모리**(토큰 하나, KV에 3만 토큰, 대역폭 51.2GB/s 계산값 기준)

| 방식 | 메모리 왕복 | 시간 |
|---|---|---|
| bf16 그대로 | 약 3.8 GB | 약 75 ms |
| 압축 저장 + 따로 풀기 | 약 8.9 GB | 약 174 ms |
| 압축 저장 + 융합 | 약 1.1 GB | 약 22 ms |

**prefill 계산량**(프롬프트 4,000토큰): 가중치 약 64조 번(97%), 어텐션 약 2.1조 번(3%). 둘이 같아지는 지점은 약 12만 토큰이다.

**KV 토큰당 메모리(bf16)**: 32층 × 4096바이트 = 128 KiB. **가중치**: 4비트로 약 4.5~5GB(추정)라 16GB에 들어간다.
