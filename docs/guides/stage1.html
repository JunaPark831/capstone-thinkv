ThinKV 1단계 — 희소도 3봉 확인 (E3)

캡스톤디자인 v2 · 기준 문서: ThinKV 구현 계획 §3.1, 논문 §3.1 관찰 1·§D.1 Algorithm 1·§E.4 · 작성 2026-10-01

1단계 목표
  1. R1-Distill-Qwen-1.5B가 생성하는 동안 디코드 스텝마다 층별 어텐션 희소도를 모은다.
  2. 층별 KDE를 그려 봉우리가 정확히 3개인 층이 있는지 본다. 이 그림이 E3다.
  3. 있으면 그 층 4개(L*)와 골 두 곳(θ₁, θ₂)을 calib.json으로 뽑는다. 없으면 분기점 A로 간다.

원논문은 3봉을 8B·70B에서만 보였다(그림 3). 1.5B에서도 나오는지가 이 계획 전체의 전제라서, 이 단계가 분기점 A다. 로드맵상 W2(9/23~9/29) 항목이라 이미 밀려 있다.

1희소도 정의

논문 각주 2: 어텐션 행 softmax(qKᵀ)에서 그 행 최댓값의 1% 미만인 칸의 비율. 디코드 스텝에서는 쿼리가 1개라 행이 헤드마다 하나다.

  • 한 층의 값 = 쿼리 헤드 12개의 희소도 평균. 계획서 §3.1의 (attn < 0.01·max).mean()과 같다.
  • 이 모델은 28층, 쿼리 헤드 12개, KV 헤드 2개(GQA)다. eager 어텐션이 넘기는 가중치는 이미 쿼리 헤드 12개로 펼쳐진 모양 (1, 12, 1, kv_len)이다.
  • 한 문제를 300토큰 생성해 본 값: 0번 층 0.78, 10번 층 0.72, 27번 층 0.57(스텝 평균). 0~1 사이 비율이다.

2수집 — calib/collect_sparsity.py

느린 수집과 빠른 분석을 파일 두 개로 나눈다. KDE 폭을 바꿔 가며 분석을 여러 번 다시 돌려야 하는데, 그때마다 생성을 다시 할 수는 없다. (계획서 §5는 calibrate.py 하나로 적혀 있다. 나누기로 하면 계획서에 이유와 날짜를 적는다.)

모델 로드. attn_implementation="eager"가 핵심이다. sdpa(기본값)에서는 어텐션 가중치가 계산되지 않아 None이 온다. kvpress는 import하지 않는다.

model = AutoModelForCausalLM.from_pretrained(
    model_name, dtype=torch.bfloat16, device_map=device, attn_implementation="eager")
assert "kvpress" not in sys.modules   # import 만 해도 어텐션이 전역 패치된다

층마다 forward hook. transformers 5.2의 Qwen2Attention.forward는 (attn_output, attn_weights)를 돌려주므로 self_attn에 hook을 걸면 가중치를 받는다. 아래 코드는 이 Mac에서 돌려서 확인했다.

n_layers = model.config.num_hidden_layers          # 28
buf = [[] for _ in range(n_layers)]

def make_hook(i):
    def hook(module, args, output):
        w = output[1]                      # eager 일 때만 채워진다: (batch, heads, q_len, kv_len)
        if w.shape[2] != 1:                # prefill 은 건너뛴다
            return
        row = w[0, :, 0, :].float()        # (heads, kv_len)
        buf[i].append((row < 0.01 * row.amax(-1, keepdim=True)).float().mean())
    return hook

handles = [layer.self_attn.register_forward_hook(make_hook(i))
           for i, layer in enumerate(model.model.layers)]

# 문제마다
for b in buf: b.clear()
out = model.generate(..., pad_token_id=tokenizer.eos_token_id)
sparsity = torch.stack([torch.stack(b) for b in buf]).cpu()   # (28, gen_len - 1)
  • .item()을 hook 안에서 부르지 않는다. 스텝마다 28번 GPU 동기화가 걸려 초당 21토큰으로 떨어졌다. 텐서로 쌓았다가 문제가 끝날 때 한 번에 옮기면 초당 약 36토큰이다.
  • 배열 길이는 생성 길이 − 1이다. 첫 토큰은 prefill에서 나오기 때문이다. 20토큰·600토큰 생성으로 (28, 19), (28, 599)를 확인했다.

데이터. 계획서대로 s1K(simplescaling/s1K-1.1, 1000문제)를 쓴다. 평가셋(MATH-500)과 겹치지 않게 하려는 것이다.

  • cot_type == "math"인 877문제만 남기고 shuffle(seed=0) 후 앞에서부터 P개.
  • s1K 문제에는 boxed 지시문이 없다(math500과 다르다). R1 권장 형식대로 "\nPlease reason step by step, and put your final answer within \boxed{}."를 붙인다.
  • 샘플링은 0단계와 같이 temperature=0.6, top_p=0.95, 시드 0. max_new_tokens=4096. s1K는 AIME급이 많아 대부분 4096에서 잘리겠지만, 캘리브레이션에 필요한 건 스텝별 희소도라 문제없다.

저장. 문제마다 파일 하나. 이미 있으면 건너뛰어 중간에 멈춰도 이어 돌릴 수 있다(0단계 JSONL과 같은 원리).

torch.save({"idx": idx, "sparsity": sparsity.half(),
            "token_ids": out[0, input_len:].cpu(), "input_len": input_len},
           f"calib/sparsity/{idx:04d}.pt")

token_ids를 같이 남기는 이유: 나중에 논문 그림 3처럼 "스텝별 희소도 + 키워드로 칠한 R/E/T 구간" 그림을 그리거나 E3′(키워드 vs 어텐션 라벨 비교)를 할 때 생성을 다시 하지 않아도 된다.

3분석 — calib/calibrate.py

CPU에서 몇 초면 끝난다. Algorithm 1의 13~31행이다.

  1. 프롬프트 p, 층 ℓ마다 희소도 배열에 KDE를 적용하고 봉우리 수를 센다.
  2. 봉우리가 정확히 3개인 층을 L*[p]에 넣는다.
  3. L* = ∩ L*[p] (모든 프롬프트에서 3봉인 층).
  4. L*의 각 층·각 프롬프트에서 봉우리 사이 골 두 곳을 θ₁, θ₂로 기록하고, 전부 평균한다.

봉우리·골 찾기. 인위적으로 만든 3봉/1봉 데이터로 확인했다.

import numpy as np
from scipy.stats import gaussian_kde
from scipy.signal import find_peaks

def modes_and_valleys(u, bw=None, prom=0.05):
    xs = np.linspace(0, 1, 512)
    d = gaussian_kde(u, bw_method=bw)(xs)
    d = d / d.max()
    peaks, _ = find_peaks(d, prominence=prom)          # 작은 출렁임은 봉우리로 안 센다
    valleys = [xs[a + np.argmin(d[a:b])] for a, b in zip(peaks[:-1], peaks[1:])]
    return xs[peaks], valleys
KDE 폭(bandwidth)이 봉우리 수를 정한다. 같은 1봉 데이터가 bw=0.1에서는 2봉으로 나왔다(Scott 기본값과 0.3에서는 1봉). bw_method에 숫자를 주면 절대 폭이 아니라 데이터 표준편차에 곱하는 배율이다. 판정은 반드시 폭 세 가지(Scott 기본, ×0.5, ×2)에서 결과가 같은지 보고 내린다. 쓴 폭과 prom 값은 calib.json에 같이 적는다.

교집합이 비거나 4개보다 적을 때. 프롬프트가 많을수록 "모든 프롬프트에서 3봉"은 거의 불가능해진다. 논문은 이 경우를 말하지 않는다. 그때는 층마다 3봉이 나온 프롬프트 비율을 세서 상위 4개 층을 L*로 쓴다. Algorithm 1 24행과 다르므로 계획서에 적는다.

그림 두 장.

  • E3 그림: 28개 층을 작은 칸(7×4)으로 나누고, 칸마다 프롬프트별 KDE를 얇은 선으로 겹쳐 그린다. 칸 제목에 3봉 비율. 논문 §E.4 그림과 비교하는 대상이다.
  • 그림 3 재현: 프롬프트 하나, L* 중 한 층. 가로 디코드 스텝, 세로 희소도(128스텝 이동평균). θ₁·θ₂를 가로선으로. 세 띠로 갈라지는지 눈으로 본다.

4분기점 A 판정

결과다음
3봉 층이 4개 이상이고 폭 세 가지에서 유지된다그대로 진행. 2단계 온라인 분류기(구현 계획 §3.1 "온라인")
3봉이 안 나온다(2봉 또는 연속)로드맵 분기점 A: (a) |T|=2로 줄여 단순 버전 재현 + "SLM에서는 전환 사고가 분리되지 않는다"를 결과로 보고, 또는 (b) Don't Waste Bits의 엔트로피·희귀도를 보조 신호로 넣는 분류기를 앞당긴다

"몇 %의 프롬프트에서 3봉이면 나온 것으로 치는가"는 계획서에 없다. 결과를 보기 전에 기준을 정해 계획서에 적어 둔다(예: 3봉 비율 50% 이상인 층이 4개 이상). 결과를 보고 기준을 맞추면 판정이 의미가 없어진다.

✓완료 기준

!막히기 쉬운 곳

  • hook에서 output[1]이 None이면 eager로 로드되지 않은 것이다. model.config._attn_implementation을 출력해 본다.
  • kvpress import 금지. 같은 파이썬 프로세스에서 eval/baseline.py의 함수를 import하는 것도 조심한다. make_press를 부르지 않으면 괜찮지만, 캘리브레이션 파일은 아예 따로 두는 게 안전하다.
  • 생성 초반 스텝은 문맥이 짧아 희소도가 다르게 움직일 수 있다. 앞 N스텝을 뺄지는 논문에 없다. 먼저 빼지 않고 그려 보고, 초반이 따로 봉우리를 만들면 그때 정한다.
  • 프롬프트 토큰도 행에 포함된다. 희소도는 프롬프트+지금까지 생성한 토큰 전체에 대한 비율이다. 논문 정의가 그렇다.
  • MPS는 같은 시드여도 비트 단위 재현이 안 된다. 다시 돌리면 생성이 달라질 수 있으니 수집 결과(.pt)를 지우지 않는다.
  • 메모리. eager는 prefill에서 (12, 입력, 입력) 가중치를 만든다. s1K 문제 길이에서는 문제없지만, 긴 문맥 프롬프트를 넣으면 커진다.

→다음 단계

3봉이 나오면 2단계: 온라인 분류기. DecodingPress를 상속한 press의 hook에서 L* 층만 마지막 쿼리 어텐션을 다시 계산해 희소도를 쌓고, 128스텝마다 θ와 비교해 R/E/T를 붙인다(구현 계획 §3.1 "온라인"). 이때는 kvpress를 쓰므로 eager가 아니라 kvpress 레시피(CAMPress._compute_current_token_attention)로 희소도를 구한다. 1단계 값과 2단계 값이 같은 문제에서 일치하는지가 2단계의 첫 확인 항목이다.

병행: GPU 확정(본 실험 E0와 6단계 Triton 커널에 필요), E3′ 키워드 베이스라인(1단계에서 저장한 token_ids를 재사용).
